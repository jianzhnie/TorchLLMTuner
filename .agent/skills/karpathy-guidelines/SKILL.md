# Karpathy 编程准则

这些行为准则源自 [Andrej Karpathy 对大语言模型编程缺陷的观察](https://x.com/karpathy/status/2015883857489522876)，旨在减少大语言模型常见的编程错误。

**权衡：** 这些准则更看重谨慎而非速度。对于简单任务，请酌情判断。

## 1. 编码前先思考

**不要臆测。不要掩饰疑惑。明确说明取舍。**

开始实现前：
- 明确说明你的假设。如果不确定，就提问。
- 如果存在多种理解，应全部列出，不要自行默默选择。
- 如果有更简单的方案，应直接说明。确有必要时，应提出异议。
- 如果有不清楚的地方，先停下来。指出疑惑之处并提问。

## 2. 简单优先

**只写解决问题所需的最少代码，不做超出需求的设想。**

- 不实现需求之外的功能。
- 不为只使用一次的代码设计抽象。
- 不添加未被要求的“灵活性”或“可配置性”。
- 不为不可能发生的场景编写错误处理。
- 如果写了 200 行代码，而 50 行就能完成，应重写。

问自己：“资深工程师会不会认为这过于复杂？”如果会，就简化。

## 3. 精准修改

**只改必须修改的内容，只清理自己造成的问题。**

修改现有代码时：
- 不要顺手“改进”相邻代码、注释或格式。
- 不要重构没有问题的部分。
- 遵循现有风格，即使你会采用不同的写法。
- 如果发现与任务无关的死代码，应指出来，不要直接删除。

当你的修改产生无用代码时：
- 删除因你的修改而不再使用的导入、变量和函数。
- 除非用户要求，否则不要删除原本就存在的死代码。

判断标准：每一行修改都应能直接对应用户的请求。

## 4. 目标驱动执行

**定义成功标准。反复验证，直到通过。**

把任务转化为可验证的目标：
- “添加校验” → “为非法输入编写测试，然后让测试通过”
- “修复 bug” → “先编写能复现问题的测试，然后让测试通过”
- “重构 X” → “确保重构前后的测试都通过”

对于多步骤任务，先给出简短计划：
```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

明确的成功标准能让你独立反复验证；模糊的标准（例如“让它能用”）则会导致不断需要澄清。
